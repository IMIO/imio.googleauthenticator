## Gap 1: one endpoint evaluates a second factor without the lockout counter

This is code-review finding CR-01 from `06-REVIEW.md`, classified CRITICAL there.
`06-VERIFICATION.md` routed it to a required human decision, and that decision was never
recorded.

**What the code does.** Three files call `helpers.validate_token`:

| File and line | Checks `is_account_locked` first | Counts a failure | Clears the counter on success |
|---|---|---|---|
| `browser/forms/token.py:133` | yes | yes, line 176 | yes, line 145 |
| `browser/forms/reset_bar_code.py:123` | yes | yes, line 170 | yes, line 145 |
| `browser/forms/user_setup.py:95` | **no** | **no** | **no** |

**Concrete failure scenario.** A caller who already holds an authenticated session — a
hijacked session, or any user whose login skipped the second factor because their client IP
is in `ip_addresses_whitelist` — opens `@@setup-two-factor-authentication` and submits
six-digit guesses. Nothing counts the failures and nothing locks the account, so the
guessing is limited only by request throughput. The replay guard inside
`helpers.validate_token` still refuses a code whose interval was already accepted, but that
guard does not limit wrong guesses. On a correct guess, `user_setup.py:121` calls
`generate_recovery_codes(user)`, which replaces all 10 stored recovery-code hashes with a
fresh set and displays the new codes.

**Why this reaches recovery codes.** `profiles/default/actions.xml:41` registers the
"Regenerate recovery codes" action with its `url_expr` pointing at
`@@setup-two-factor-authentication` — the same form as first enrolment. The comment above
that entry states the design intent plainly: "that form validates a currently valid TOTP
code before it writes, so a user holding only a recovery code cannot mint a fresh set from
one. No dedicated regeneration view exists or should be added; that device-possession check
is the gate." The gate named there is the unthrottled call at line 95.

**Why no test caught it.** None of the five ROADMAP Phase 6 success criteria, and no
`must_haves.truths` entry in `06-01-PLAN.md`, `06-02-PLAN.md` or `06-03-PLAN.md`, asserts
that this endpoint is rate-limited. RECOV-05 says recovery-code attempts must increment the
same counter as TOTP attempts, and they do — at the login form. MFA-08 names no endpoint at
all, which is why the shortfall is a judgment call rather than a mechanical test failure.

**What closing it would look like.** `browser/forms/reset_bar_code.py` already has the
shape: check `is_account_locked(user)` before validating, call
`validate_token(token, user=user)`, then call `reset_failed_second_factor(user)` on success
and `register_failed_second_factor(user)` on failure. `user_setup.py`'s `handleSubmit` runs
in a committing view, so it satisfies MFA-12's constraint that all second-factor state
writes happen where the transaction commits. Note that v1.1 requested item 4 ("Require
password re-authentication before enabling or disabling MFA, or regenerating recovery
codes") addresses the same endpoint by a different mechanism, so any decision here should
account for whether one supersedes the other.

## Gap 2: the uninstall profile is narrower than COEX-06's wording

COEX-06 reads "A real `profiles/uninstall/` restores anything the install profile changed."
What shipped and was verified is narrower, and the narrowing was deliberate: plan 07-03
scoped the uninstall profile to exactly the two resources this package owns, and pinned that
scope with `test_profile_only_registers_resources_it_owns` so no future edit can name a
resource belonging to `imio.dms.mail`.

`profiles/uninstall/` contains `jsregistry.xml` and `cssregistry.xml`, which unregister
`++resource++imio.googleauthenticator/main.js` and `main.css`. `profiles/default/` also
ships `registry.xml`, `actions.xml`, `memberdata_properties.xml`, `browserlayer.xml`,
`controlpanel.xml`, `propertiestool.xml` and `site_properties.xml`. The uninstall profile
reverses none of those, and no test in this repository asserts what Plone 4.3's
QuickInstaller does with them on its own.

Leaving the registry records behind is arguably correct: discarding `ska_secret_key` would
invalidate every previously-issued signed URL, and discarding the stored seeds would strand
enrolled users on a reinstall. The three `portal_actions` entries are the part most likely
to remain visible to a user after an uninstall. This is recorded as a mismatch between
wording and delivered scope, to resolve in `REQUIREMENTS.md`, not as a defect to fix in
code.

## The operational blocker, which is not a code gap

The seed encryption key must reach every ZEO client as the environment variable
`IMIO_GOOGLEAUTHENTICATOR_SEED_KEY`. It is supplied by a Puppet `concat::fragment` in the
separate `industrialisation` repository, and that change has not shipped.

`base.cfg:54` sets the variable in the `[testenv]` section only, with a comment marking it a
throwaway test-only key. The `[test]` section reads `[testenv]`, which is why `bin/test`
carries the value and `bin/test-coverage` inherits it by invoking `bin/test`. The
`[instance]` section sets no such variable, so `bin/instance` gets the key only from the
external Puppet fragment or a manual `export`. Per SEC-08, a missing key logs CRITICAL at
process start rather than raising, so a production instance would start normally and then
refuse every enrolment and every login that needs a seed.

The package is code-complete, tested and green. It is not deployable until that Puppet
change ships. This has been tracked since Phase 3 and is restated here so it does not fall
through the milestone close.
