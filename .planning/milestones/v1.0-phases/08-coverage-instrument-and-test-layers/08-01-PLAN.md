<objective>
Repair the build's measuring instrument end to end, in one commit, before any new test exists.
`.coveragerc` gains the `[run]` section that scopes measurement to package code with branch
coverage on (QUAL-01); the `[test-coverage]` template gains `set -e` so a failing test fails the
build (QUAL-02); the `[coverage]`/`[test-coverage]` buildout parts are enabled, `coverage == 5.5`
pinned and `createcoverage` dropped (QUAL-03). Then the `set -e` fix is proven with a real red
build, not by inspection.

Purpose: this is the phase's first commit because every later plan is judged by this instrument.
Per ROADMAP §Same-Commit Requirements and CONTEXT.md D-07, QUAL-01 and QUAL-02 must not be split —
a corrected `.coveragerc` without `set -e` still calls a red suite green, and `set -e` without the
corrected `.coveragerc` gates on a figure that counts test modules as covered code.
Output: a working `bin/test-coverage` whose exit code means something, plus the re-measured
coverage-5.5 baseline that plan 08-04 consumes.
</objective>

## Flagged planner assumptions (edge probe: unresolved)

The deterministic edge probe classified QUAL-01, QUAL-02 and QUAL-03 as `unclassified`, so each
stays `unresolved` and is surfaced here rather than silently dropped or auto-backstopped. These are
build-instrument requirements, not data-shape edge cases, so the classifier had nothing to match —
a truthful result, not a probe failure.

- **QUAL-01 (unresolved).** Assumed: correctness of the instrument is provable by *report shape*
  (the presence of `Branch`/`BrPart` columns and the absence of `tests/` rows), not by a unit test.
  No test file asserts on `.coveragerc`. If a reviewer wants a permanent regression guard on the
  config, that is a gap this plan does not close.
- **QUAL-02 (unresolved).** Assumed: the red-build proof is a one-off, then-reverted mutation and
  leaves **no permanent test artifact**. Nothing in the suite will notice if `set -e` is later
  deleted from the template.
- **QUAL-03 (unresolved).** Assumed: buildout-level correctness is provable only by running
  `bin/buildout` and inspecting the generated scripts. No automated check prevents `createcoverage`
  from being re-added to `parts` later.
