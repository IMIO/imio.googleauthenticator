# Milestone Context — v1.1 (proposed)

Captured 2026-08-06, at the close of milestone v1.0. Written so `/gsd-new-milestone`
picks the scope up directly rather than re-gathering it from conversation.

## Requested features, as the operator wrote them

These eight items are recorded verbatim. Do not treat my grouping or interpretation
below as a substitute for them.

1. After MFA setup, redirect to home page instead of user profile.

2. Make sure globally enabled makes the MFA compulsory. When not globally enabled,
   allow users to enroll by themself. Enrollment never blocked unless package is
   uninstalled.

3. Fix: Existing users don't have MFA forced if imio.googleauth is installed later.

4. Require password re-authentication before enabling or disabling MFA, or
   regenerating recovery codes.

5. Show the secret in text form alongside the QR (people use password managers and
   desktop TOTP clients).

6. Email on every MFA state change (MFA enabled, MFA disabled, recovery codes
   regenerated), with no opt-out.

7. Fix missing French translations. Named examples: "These codes are shown only this
   one time and cannot be retrieved again.", "regenerate recovery codes", "Enter the
   verification code generated by your mobile application. If you have somehow lost
   your bar code, request a bar code reset here."

8. As an admin, when visiting a user profile (`/@@user-information?userid=agent`),
   remove "Cliquez ici pour la configurer ou ici pour la désactiver." in the
   description of the field "Activer la vérification en deux étapes." Because links
   lead to a view related to the current user, not the visited user profile. The links
   are "@@setup-two-factor-authentication" and "@@disable-two-factor-authentication".
   (Clarified by the operator 2026-08-06, replacing an earlier shorter wording.)

## Two open items already tracked, which belong in this milestone

Neither is new. Both are recorded in the repository already and are unassigned to any
phase. They should be folded into v1.1 rather than re-raised as fresh requirements.

- **MFA-14** (in the v1.0 `REQUIREMENTS.md`, status `Unassigned`): turning on
  `globally_enabled` must cover accounts that already exist when the add-on is
  installed, not only accounts created afterwards. Today enrolment of existing users
  happens only when an administrator saves the settings control panel form
  (`browser/controlpanel.py:125-132`); `setuphandlers.setupVarious` enrols nobody, and
  the login gate consults each user's own `enable_two_factor_authentication` flag,
  never the global setting. Found 2026-08-05 during Phase 7 plan 07-04 verification on
  a real two-egg environment: installing `imio.dms.mail` first left an existing Member
  unenrolled; the reverse order enrolled them. Three candidate remedies are in the Gaps
  section of `.planning/phases/07-coexistence-with-imio-dms-mail/07-UAT.md`.

  **This is the same problem as requested items 2 and 3 above.** Items 2 and 3 are not
  new requirements; they are MFA-14 finally getting a phase.

- **A rejected recipient address crashes the bar-code reset email path.**
  `src/imio/googleauthenticator/browser/forms/request_bar_code_reset.py:112-113`
  catches `SMTPRecipientsRefused` and re-raises the same exception type. The only
  enclosing handler catches `ValueError`, which that exception is not, so the caller
  gets an unhandled error instead of the in-page failure message every other failure
  path in that method uses. It predates the fork — `git log -S` places its first
  appearance in the phase 1 rename commit — and has never had a test; those lines still
  show as uncovered in the coverage report. Recorded as finding CR-01 in
  `.planning/phases/08-coverage-instrument-and-test-layers/08-REVIEW.md`.

  Requested item 6 adds email sending on every MFA state change, which makes the
  package's mail-failure behaviour load-bearing in more places. Fixing this crash
  belongs in the same milestone as item 6, and arguably before it.

## Item 8 confirmed against the code — it is a wrong-account defect, not a cosmetic one

Verified 2026-08-06 by reading the source. The severity is higher than the phrasing of
the request suggests, so this is recorded separately rather than left as a wording fix.

**What the code does today.**
`src/imio/googleauthenticator/userdataschema.py:76-83` declares the
`enable_two_factor_authentication` field. Its `description` hardcodes two relative
links: `@@setup-two-factor-authentication` and `@@disable-two-factor-authentication`.

`src/imio/googleauthenticator/browser/disable_two_factor_authentication.py:25` calls
`api.user.get_current()` to pick the account it modifies. A grep for `userid`,
`user_id` and `REQUEST.get` across that view and `browser/forms/user_setup.py` returns
no matches — neither view accepts a target user from the request.

**The consequence.** An administrator viewing `/@@user-information?userid=agent` sees
those two links inside the field description. Clicking the disable link runs
`DisableTwoFactorAuthentication.disable()`, which clears
`enable_two_factor_authentication`, `two_factor_authentication_secret` and
`bar_code_reset_token` on the **administrator's own account**, then redirects to the
administrator's own `@@personal-information`. The success message says "You have
successfully disabled the two-step verification for your account." Nothing indicates
the intended target was untouched. An administrator trying to help a locked-out user
silently removes their own second factor instead.

**What was asked for.** Remove that sentence from the field description when the form
is rendering another user's profile (`@@user-information`), so the misleading links are
not offered there. The request is scoped to removing the links, not to building an
administrator-facing disable feature for another account.

**Left open for planning, not decided here.**
- Whether the sentence should still appear on a user's own profile
  (`@@personal-information`), where the links do target the right account. Removing it
  everywhere is simpler; keeping it on the own-profile form preserves a working
  shortcut. `browser/settings_helper.py` already decides which menu links to show and
  may be the right place for the condition.
- Whether an administrator should get a working way to disable another user's second
  factor. That is a new feature, not part of this request, and it would need its own
  permission check and its own audit trail.
- Whether the two views should refuse to act when a `userid` parameter is present that
  does not match the logged-in user. That would close the trap at the view rather than
  only hiding the link, and would also cover a bookmarked or hand-typed URL.

**Note on adjacency.** Requested item 1 changes where the setup flow redirects after
enrolment. The disable view's own redirect to `@@personal-information` sits in the same
code area (`disable_two_factor_authentication.py:38`). Planning may want these together.

## Open questions to settle before planning

These are genuine ambiguities, not rhetorical prompts. Each one changes what gets
built. They belong in `/gsd-discuss-phase` or `/gsd-spec-phase`, not in a guess made
while capturing scope.

**On item 4 — password re-authentication scope and lifetime.**
- How long does a successful re-authentication stay valid? Single action only, or a
  short window covering several changes?
- Does it apply when an administrator disables MFA on someone else's account, or only
  to a user acting on their own account?
- Interaction with the existing lockout counter: does a failed password re-auth feed
  the same failure counter that wrong TOTP codes feed (`MFA-08`..`MFA-13`), or a
  separate one? Feeding the same counter means a user can lock their own account out of
  the login form by mistyping their password on a settings page.

**On item 6 — behaviour when the mail send fails.** The project already has one
unhandled mail-failure path (see the CR-01 item above). Decide explicitly: does a
failed notification email block the MFA state change, or does the state change proceed
and the failure get logged? "No opt-out" fixes who receives the mail; it does not
answer what happens when delivery fails.

**On item 5 — the secret shown in text form is a real disclosure change.** The QR code
already encodes the secret, so a viewer of that page can already extract it. Showing it
as text does not add a new secret to the page, but it does make it copyable and
shoulder-surfable. Confirm this is intended, and decide whether it needs the same
password re-authentication gate as item 4.

**On item 2 — what "enrollment never blocked unless package is uninstalled" means for
the lockout feature.** The package currently locks an account after N failed second-factor
attempts. Confirm whether "never blocked" is about enrolment only (a user can always
start enrolling) or is intended to override the existing lockout behaviour, which would
contradict `MFA-08`..`MFA-13` shipped in Phase 5.

## Constraints carried forward from v1.0

Unchanged and still binding — see `.planning/PROJECT.md` for the full list.

- Python 2.7.18 and Plone 4.3 only. Nothing may require PEP 517.
- Must coexist with `imio.dms.mail`: no wholesale skin or resource-registry overrides,
  and nothing that mutates a resource this package does not own.
- The seed encryption key never lives in the ZODB, a memberdata property, a log line,
  or an exception message.
- Every new memberdata property needs a `memberdata_properties.xml` entry and a
  set/get round-trip test, because `MutablePropertySheet.setProperties` silently pops
  undeclared properties.
- Test coverage stays above 90%, enforced in CI by `bin/test-coverage -t !robot`.
- `bin/code-analysis` must keep exiting 0 — the pre-commit hook now depends on it.
- The package is retired for Keycloak in roughly one to two years. That caps how much
  any fix is worth and is why Python 3 and Plone 6 migrations stay out of scope.
