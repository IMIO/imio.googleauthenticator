<objective>
Close UX-01 and UX-02: send the user somewhere useful after enrollment, and hand them a secret
they can actually copy.

UX-01 — a user who finishes enrollment lands on the recovery-codes page, whose only link points at
their own profile. That link becomes the site home page. It must be done in the template: the
success path in `handleSubmit` leaves `redirect_url = None` on purpose, because
`plone.z3cform` 0.8.1's `FormWrapper.update()` blanks the wrapped form only on a 302/303 response
— the one-time recovery-code display exists precisely because that response is not a redirect.
Restoring a redirect there would undo RECOV-03. The source says so in a comment block that is
there to stop exactly this.

UX-02 — the enrollment page shows a QR code but no copyable text form of the same secret. The QR
already encodes it, rendered locally with no gate at all, so the text hands out no secret the page
did not already hand out; it adds shoulder-surfability and screenshot-readability to a value
already on screen, and Phase 11's SEC-09 puts a password prompt in front of this same action later.

Purpose: the two usability gaps on the enrollment path, both single-file, both cheap.

Output: a retargeted link in `recovery_codes.pt`, an extended `get_token_description()` in
`helpers.py`, and one test per requirement in `tests/test_user_setup.py`.

Decisions implemented: D-01 (retarget the existing link, do not add a second one and do not add a
form handler), D-02 (resolve the home page the way this package already resolves it), D-03 (leave
the non-site-local refusal redirect alone), D-04 (the new link text), D-05 (UX-02 stays in this
phase), D-06 (always visible, no reveal control, no JavaScript), D-07 (the base32 secret only, not
the `otpauth://` URI), D-08 (produced by extending `get_token_description()`, staying inside the
site-local branch).

UX-02 is the requirement most at risk of being over-built. It is one string emitted beside an image
that already encodes the same value. A reveal control, a second schema field, a custom template and
a second representation of the secret were all considered and all rejected for the same reason: the
QR next to it already gives away everything the text does. Build the one string.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated user browser -> `@@setup-two-factor-authentication` | The rendered page carries the user's plaintext TOTP seed, today as a QR image and after this plan also as text. Anything visible on this page is visible to a shoulder-surfer and to a screenshot. |
| `SetupForm.updateFields` -> `helpers.get_or_create_secret` | A render path reaches a function that can mint and store a seed. Which branch reaches it decides whose account gains state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-04 | Information Disclosure | base32 secret rendered as text on the enrollment page | low | accept | The QR beside it already encodes the same secret and is rendered today with no gate at all, so the text adds no secret the page did not already hand out — it adds shoulder-surfability and screenshot-readability to a value already on screen (D-05). Phase 11's SEC-09 puts a password prompt in front of this same enrollment action, and the display inherits that gate without the requirement having to move. Accepted for this phase on that basis. |
| T-09-05 | Tampering / Denial of Service | `get_token_description()` reaching `get_or_create_secret()` | medium | mitigate | A display path that minted or rotated a seed would invalidate an already-enrolled authenticator and lock the user out. Keep the single existing call with its existing `overwrite=overwrite_secret` argument, bind its result once and reuse it; add no second call and no new default. The existing T-03-23 test's "no seed stored for an unprotectable account" assertion is the standing regression guard. |
| T-09-06 | Information Disclosure | secret leaving the page it is rendered on | medium | mitigate | The secret must not gain a second home as a side effect of being displayed: no `logger` call receives it, no email carries it, no memberdata property or cache stores it beyond the one encrypted seed that already exists. Enforced by the diff scope — the change is a format string in one function. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task in this plan. `qrcode` and `cryptography` are already pinned and installed; no dependency is added or changed. |
</threat_model>
