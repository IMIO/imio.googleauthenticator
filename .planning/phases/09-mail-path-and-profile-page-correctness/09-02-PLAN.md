<objective>
Close BUG-08: remove the two links from the `enable_two_factor_authentication` field description.

Neither of the two views those links point at accepts a target user from the request — both act on
`api.user.get_current()`. An administrator who clicks the disable link while viewing someone else's
profile at `/@@user-information?userid=<other>` clears their **own** seed, reset token and enable
flag, and is told it succeeded.

The fix has a counter-intuitive shape and the executor should hold it in mind while working:
the obvious reading — "an administrator sees links they should not, so hide them from
administrators" — is wrong. `CustomizedUserDataPanel.__init__` omits this field from
`@@personal-information`, so the admin-facing `@@user-information` form is the *only* place this
description renders. The user who ought to have those links never sees them here at all; their
route is the portal actions in `profiles/default/actions.xml`, which build correct
`navigationRootUrl` URLs and are Phase 10's business. So the fix is a deletion, and it makes no
user worse off.

Purpose: remove a confused-deputy affordance that can silently weaken an administrator's own
account.

Output: a one-sentence description on the schema field, and one schema-level test asserting the
links are gone.

Decisions implemented: D-14 (delete outright, do not make the description conditional), D-15 (the
replacement is the first sentence already present), D-16 (do not hand-edit the catalogues),
D-17 (the test asserts absence of the view names, not the replacement wording).

Explicitly out of scope, and it will look tempting from inside this file: refusing a mismatched
`userid` at the two views themselves. That is a Future Requirement in `REQUIREMENTS.md` with its
residual risk already recorded — a bookmarked or hand-typed disable URL still disables the
clicker's own second factor and reports success. Do not add it here.

One task is the whole plan: an eight-line test and a three-line deletion, with the mandatory
non-vacuity check between them.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| administrator browser -> `@@user-information?userid=<other>` | An authorized viewer acts on a page describing a *different* principal. Any affordance rendered here that operates on the current user rather than the viewed user crosses a principal boundary the page's own framing denies. |
