<objective>
Close BUG-07: make a failed bar-code reset email report itself the way every other failure in
`RequestBarCodeResetForm.handleSubmit` already reports itself, instead of escaping as an unhandled
exception.

Today `request_bar_code_reset.py:112-113` catches `SMTPRecipientsRefused` and re-raises the same
exception type. The enclosing `except ValueError:` cannot catch it, so it leaves `handleSubmit`
entirely and the caller gets a framework error page. Those two lines are also currently uncovered,
so the fix has to ship its own test to keep the 90% branch-coverage gate honest.

Purpose: Phase 12 attaches three more senders to this same mail path. The failure shape settled
here (D-09, D-10, D-11) is the shape those three will copy, so it lands first.

Output: a widened, non-re-raising catch in `request_bar_code_reset.py`, plus two new failure-path
test methods and a raising `MailBase._send` harness variant in
`tests/test_request_bar_code_reset.py`.

Decisions implemented: D-09 (catch every SMTP-level and network-level send failure, not only the
named one), D-10 (delete the re-raise outright), D-11 (reuse the existing generic message and log
the real cause with `logger.exception`), D-12 (do not roll back the already-written reset token),
D-13 (reuse the existing `MailBase._send` harness; mandatory non-vacuity check).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `@@request-bar-code-reset` | The form is registered `permission="zope2.View"` and is reached by a caller whose `__ac` cookie the PAS plugin has already cleared. Untrusted username input crosses here. |
| Zope process -> SMTP server | `host.send(..., immediate=True)` leaves the process and can fail in ways the application does not control. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-02 | Information Disclosure | `RequestBarCodeResetForm.handleSubmit` failure messages | low | accept | Pre-existing username-enumeration oracle on this unauthenticated form, accepted at low severity as T-03-26. D-11 preserves the mitigation by reusing the generic `_("An unexpected error occurred.")` rather than a distinct "we could not email that address" message, which would tell an anonymous submitter whether a username has a deliverable address.
