- Installing the add-on with `globally_enabled` on now sets the second-factor requirement for every
  account already in the site, and those accounts are walked through enrollment at their next login.
- With `globally_enabled` on, neither a user nor an administrator can turn a second factor off; turn
  the setting off first.
- A new member-data property, `two_factor_authentication_enrolled`. It is internal state with no
  profile-form field, and it is not removed by the uninstall profile.
- The one consequence for an account that was already enrolled before this phase: it is shown the
  enrollment page once, its existing authenticator still produces accepted codes because the QR
  renders its existing seed, and completing that page mints a fresh set of recovery codes which are
  displayed in the same response — so the previous set stops working. Written down because it is
  surprising, and because no deployed site exists yet (the seed-key Puppet fragment has not shipped)
  so it was accepted rather than migrated.

- The seed minted while signing an enrollment redirect is discarded on the `challenge()` path,
  because that transaction is already aborted, so a first-time enrollee reached that way sees a
  refusal and must retry through the login form. Pre-existing behaviour described in
  `subscribers.py`; more often reached now.
- `browser/controlpanel.py`'s commented-out bulk-disable call stays commented out — STATE.md's open
  Future Requirement.
- Refusing a mismatched `userid` at `@@setup-two-factor-authentication` and
  `@@disable-two-factor-authentication` is still a Future Requirement carried over from Phase 9.
- The `IMIO_GOOGLEAUTHENTICATOR_SEED_KEY` Puppet fragment still has not shipped from the
  `industrialisation` repository. Nothing in this phase changes that, and it is still what stands
  between code-complete and deployable.
