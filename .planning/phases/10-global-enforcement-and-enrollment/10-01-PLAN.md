<objective>
The tracer slice for this phase: one production-quality path from install to a logged-in,
enrolled user, wired through every layer the phase touches.

Install enrols a pre-existing account (flag only, no seed — D-01/D-02). That account logs in and
is routed to the enrollment page instead of the code-entry page (D-05/D-06). The enrollment page
identifies it from an `ska`-signed `auth_user` parameter on a cookie-cleared request and renders
the QR code (D-16). Submitting a valid code marks enrollment complete, establishes the session,
and shows the recovery codes (D-17).

This is the one path whose failure is a site-wide lockout, so it is proven end to end before any
expansion work starts. MFA-15 and MFA-19 are one deliverable and both live in this plan.

Purpose: prove the architecture end-to-end on one account before four expansion plans build out
from it. If the routing or the sessionless identity resolution is wrong, it is wrong after one
commit, not after nine.
Output: a new member-data property, two read/write helpers, an install-time enrollment step, a
login routing decision, a sessionless-capable enrollment form, and one end-to-end test.
</objective>

<assumption_delta_decision>
Detector fired: `pluralization`, term `second`, on the roadmap goal's phrase "presents a second
factor". The literal trigger is a false positive — "second factor" is this package's domain noun,
not a second instance of a thing that used to be singular.

The underlying question is real, though, and worth an answer: this phase adds a second per-user
question ("has this account completed enrollment?") alongside the existing one ("is a second
factor required for this account?").

- **Noun that is now primary:** still `enable_two_factor_authentication`. It alone decides whether
  a login is intercepted (D-03). The new property decides only *where* an intercepted login is
  sent.
- **Decision: `add-alongside`.** The two booleans are independent facts, not a generalisation of
  one fact. Requirement and enrollment-completion are set by different actors at different times
  (install/control panel/creation handler vs. the user's own first accepted code). Collapsing them
  into one enum property would make `has_enabled_two_factor_authentication` — read by the PAS
  plugin, the two disable views, and three link conditions — a derived value, for no gain.
- **Accepted debt:** the observable state space is now three-valued (not required / required but
  not enrolled / enrolled) encoded across two booleans plus seed presence. If a fourth state ever
  appears — the most likely being "enrollment in progress on a specific device" — the implicit
  encoding stops being readable and the pair should be promoted to a single enum member-data
  property with the two booleans derived from it.
</assumption_delta_decision>

  <behavior>
    - A request carrying a valid signed `auth_user` for account X, with no `__ac` cookie, renders
      the enrollment form with the QR-code markup for X.
    - Submitting a valid TOTP for X on that request sets `enable_two_factor_authentication` True,
      sets `two_factor_authentication_enrolled` True, establishes a session for X, and renders ten
      recovery codes in the same 200 response.
    - A request with no `auth_user` and no session is refused with 401 and renders no QR code.
    - A request whose `auth_user` names a username `api.user.get()` cannot resolve is refused and
      renders no QR code.
    - A request whose `auth_user` resolves but whose signature does not validate gets an error
      status message, no QR code, and no token is evaluated.
    - The eleven existing methods in `tests/test_user_setup.py` behave identically — they run
      authenticated with no `auth_user`, so the resolved user is `api.user.get_current()`.
  </behavior>
  <action>
**`browser/forms/user_setup.py`.**

Add a private `_resolve_signed_user()` method returning a `(user, signed)` tuple, built from
`token.py:107-122` rather than invented:

- Read `self.request.get('auth_user', '')`. If it is empty, return
  `(api.user.get_current(), False)` when the request is not anonymous, and `(None, False)` when it
  is. This is the branch every existing authenticated test takes, unchanged.
- If it is non-empty, resolve `api.user.get(username=username)`. If that is `None`, return
  `(None, False)` — an `auth_user` naming an account that does not exist gets no QR and no token
  evaluation.
- Otherwise call `validate_user_data(request=self.request, user=user)`. On a falsy `.result`,
  return `(None, False)`. On success return `(user, True)`.

Import `validate_user_data` and `drop_login_failed_msg` from `imio.googleauthenticator.helpers`,
matching `token.py:5-11`'s import style. Do not build a second signing or session-establishment
scheme — `validate_user_data` and `acl_users.session._setupSession` are the only two mechanisms in
this package for these jobs, and a second one would be an unreviewed attack surface.

Replace the unconditional anonymous 401 at the top of `handleSubmit` with a call to
`_resolve_signed_user()`. When the returned user is `None`, keep exactly the existing refusal —
`setStatus(401, ...)` and `return False` — so an unsigned anonymous request is refused as it is
today. When `_resolve_signed_user` refused because a signature failed validation rather than
because the request was plain anonymous, also queue an `IStatusMessage` error naming invalid data,
mirroring `token.py:118-122`; a new translatable msgid, D-12's constraint applies (it must not
state anything about other accounts).

Thread the resolved user through the rest of `handleSubmit` in place of the
`api.user.get_current()` call at line 102: `is_site_local_user(user)`, `is_account_locked(user)`,
`validate_token(token, user=user)`, `reset_failed_second_factor(user)`,
`register_failed_second_factor(user)`, `generate_recovery_codes(user)`. Leave the ordering of
those calls, the `reason` variable, and the whole RECOV-03 comment block and its `redirect_url`
logic exactly as they are — the comments at lines 104-120 and 162-176 explain two separate traps
(a message-plus-response oracle, and the one-time recovery-code display depending on the response
*not* being a 302) and both still apply.

Inside the existing success `try:`, immediately after the
`enable_two_factor_authentication` write and before the success `IStatusMessage`, call
`mark_enrollment_completed(user)`. This must run on **every** success path, not only the signed
one: a self-enroller whose enrollment-completion property stayed False would be routed straight
back to this page at their next login, forever. Then, still in the success branch and only when
`signed` is true, call `self.context.acl_users.session._setupSession(username, self.context.REQUEST.RESPONSE)`
with the unicode username straight from the request — `token.py:147-153` records why it must not be
`str()`-coerced (`UnicodeEncodeError` on any non-ASCII character, WR-03). Do not add a redirect
after it; RECOV-03 depends on this response staying a 200 so the codes render.

Restructure `updateFields` so it calls `super(SetupForm, self).updateFields(*args, **kwargs)` on
every path. Today that `super()` call sits *inside* the `if bool(api.user.is_anonymous()) is False:`
block, so an anonymous request gets no field update at all — half of why the page is unusable for
a redirected user. Resolve the user through `_resolve_signed_user()` and render the barcode
description with `get_token_description(user)` when a user was resolved, keeping the existing
`is_site_local_user` branch and its T-03-23 comment verbatim (that comment explains that
`get_token_description` mints a seed as a side effect, which is exactly why the non-site-local arm
must not render it). When no user resolves, leave the field description untouched and still call
`super()`.

Also in `updateFields`, when the request arrived signed, call `drop_login_failed_msg(self.request)`
— the credentials were wiped by `authenticateCredentials`, which queues a spurious "Login failed"
message that would otherwise render above the QR code. Do **not** copy `token.py`'s
`response.setCookie('__ac', '', path='/')` line: `send_2fa_redirect` already cleared that cookie,
and clearing it unconditionally here would log out an authenticated user in the middle of ordinary
self-service enrollment. Record that as a deliberate deviation from `token.py` in a comment, per
this repo's convention of commenting deliberate deviations in the source rather than only in
planning documents.

Add an `action()` method copied from `token.py:57-61`, returning `self.request.getURL()` joined to
`self.request.get('QUERY_STRING', '')` with a `?`. Without it z3c.form posts back to the bare URL
and the signed `auth_user` and signature are dropped on submit, so the token submission arrives
unidentifiable — the failure would look like a working page that 401s the moment you press Verify.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `@@setup-two-factor-authentication` | An anonymous, cookie-cleared request now reaches a page that renders a TOTP seed. The only thing identifying the caller is the `ska` signature in the query string. |
| browser -> PAS `authenticateCredentials` | Untrusted login credentials cross here; the routing decision made from them selects which page the user is sent to. |
| GenericSetup import step -> `portal_memberdata` | Install writes a security-relevant flag for every account in the site. |

## STRIDE Threat Register

ASVS L1, block on high.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Spoofing | `SetupForm._resolve_signed_user` | high | mitigate | Resolve the user from `auth_user`, then `validate_user_data(request, user)` against **that same** user. The signing key includes that user's own seed (`get_ska_secret_key`), so a signature minted for account A does not validate for account B. Refuse when the username does not resolve. |
| T-10-02 | Elevation of Privilege | `SetupForm.handleSubmit` `_setupSession` call | high | mitigate | `_setupSession` runs only inside the valid-token branch, only when `_resolve_signed_user` returned `signed=True`, and only after `validate_user_data` succeeded — the same ordering `token.py:143-153` uses. A failed signature returns before any token is evaluated. |
| T-10-03 | Information Disclosure | `SetupForm.updateFields` barcode description | high | mitigate | The QR/secret markup is rendered only for a resolved user: a valid signature for that user, or an authenticated self-service session. No resolution means no `get_token_description` call, which also means no seed minted as a rendering side effect. |
| T-10-04 | Denial of Service | `setuphandlers._enroll_existing_users` + login routing together | high | mitigate | MFA-15 does not ship without MFA-19: this plan's single end-to-end test is the gate. `api.user.get_users()` returns site-local accounts only, so the Zope-root account is never enrolled and stays the operator's way back in. |
| T-10-05 | Tampering | `_mark_2fa_pending`'s new routing key | medium | mitigate | Written with `request.set` and read only through `request.other.get`, never the request's general accessor — which falls through to form data and cookies and would make a forged `?_2fa_enrollment_needed=1` attacker-controlled. Same rationale `subscribers.py`'s docstring already records for the pending key. |
| T-10-06 | Denial of Service | `send_2fa_redirect` on the `challenge()` path | medium | accept | Signing the enrollment target mints a seed; on the already-aborted `challenge()` transaction the mint is discarded and the resulting signature will not validate, so the user sees a refusal and must retry through the login form. Pre-existing behaviour, documented in `subscribers.py`, reached more often here. Self-healing on retry, fail-closed, no bypass. Carried as a residual in plan 06. |
| T-10-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task exists in this phase. RESEARCH.md records that no new third-party package is introduced and that the Package Legitimacy Gate is not applicable. |
</threat_model>
