<objective>
Expand the tracer's install half into the full MFA-15 matrix, and settle the one assumption
RESEARCH.md flagged as unverified: that letting an exception propagate out of
`setuphandlers.setupVarious` really is "reporting plainly" (D-04).

This plan is where the second of the three Wave 0 test gaps closes — no existing test in the whole
suite raises an exception from inside `setupVarious`, so nothing today proves what an operator
actually sees when install-time enrollment fails partway through a user list.

Purpose: MFA-15 is a security control applied in bulk to every account on a site. The interesting
cases are all the ones the happy path does not cover — zero users, a second install, the setting
off, one account failing, and an account this plugin cannot gate at all.
Output: five new test methods, and whatever change to `_enroll_existing_users` they turn out to
require.
</objective>

`test_install_enrolls_every_pre_existing_account_without_a_seed` (D-01/D-02, MFA-15). Set

`test_install_enrollment_is_idempotent_across_two_profile_applications` (D-13, MFA-15 adjacency

a re-mint would silently invalidate a working authenticator, and that
`two_factor_authentication_enrolled` was not reset to False, which would route an enrolled user
back to the QR page at their next login.

`test_install_enrolls_nobody_when_globally_enabled_is_off` (D-01, MFA-15). Set
`globally_enabled` False, create two accounts, apply the profile, assert neither flag was set. Then

two-halves structure — set `globally_enabled` True, apply again, and assert both flags now are set.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GenericSetup import step -> `portal_memberdata` | Install writes a security-relevant flag for every account in the site, inside the install transaction that QuickInstaller snapshots. |
