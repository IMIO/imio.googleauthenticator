<objective>
MFA-17 and MFA-18: a user can enrol themselves from their own profile when `globally_enabled` is
off, and the enrollment flow is reachable whatever the global setting says.

Both link conditions in `browser/settings_helper.py` are inverted today and their own docstrings say
so — the code requires `is_two_factor_authentication_globally_enabled()` to be **True** where the
docstring says False. This plan settles that in favour of the docstrings (D-10, D-11).

It also closes the regression D-11 would otherwise cause. `profiles/default/actions.xml` gives the
"Regenerate recovery codes" action the disable link's condition, deliberately, with a comment saying
why. D-11 changes that condition to require the global setting to be off, which would hide
"Regenerate recovery codes" from every user under global enforcement — exactly the population that
needs it (D-15).

This is also where the first of the three Wave 0 test gaps closes: there is no
`tests/test_settings_helper.py` and zero coverage of that module today. It is created from scratch.

Purpose: these three booleans are the route an ordinary user takes to enrollment. Getting them wrong
does not raise anything — it just quietly removes a menu entry, which is how the
`regenerate_recovery_codes` coupling went unnoticed until RESEARCH.md read `actions.xml` directly.
Output: three corrected/added methods, one view registration, one action rewired with its comment
brought up to date, and a new test module carrying the four-case matrix.
</objective>

<planner_notes>
**A deliberate deviation from RESEARCH.md's "Recommended shape", and the reason for it.**

RESEARCH.md (section "Recommended shape for `settings_helper.py`") proposes
`show_enable_two_factor_authentication_link` return `not has_enabled_two_factor_authentication(user)`.
That is wrong for this phase, and the four-case matrix is what shows it.

Under D-01, install sets `enable_two_factor_authentication` for every pre-existing account. With
RESEARCH.md's shape, `has_enabled_two_factor_authentication` is then True for all of them, so the
enable link is hidden from every single install-enrolled user — the exact population MFA-19 exists
to walk through enrollment. Success criterion 5 ("no combination of settings leaves a user unable to
enrol") would fail on its most common case, the first login after install.

So the enable link's condition is `not has_completed_enrollment(user)` — the property plan 10-01
added. That covers both populations the same way: a user who never enabled anything (flag off,
property off) and a user enrolled by install (flag on, property off) both get the link; a user who
has actually completed enrollment does not. This is the honest reading of D-10's own wording:
"offer the link based on whether the user is enrolled, not on the global setting."

D-11's disable condition keeps `has_enabled_two_factor_authentication` verbatim per RESEARCH.md,
deliberately, and the two are not inconsistent: the disable action's *subject* is the enable flag —
it is the thing being turned off — so the flag is the right predicate for whether turning it off is
a meaningful offer. It also means a user who abandoned self-enrollment (flag on, property off, global
off) still sees the disable link, which is their way out of a requirement they never completed.

**Why D-15 is load-bearing for success criterion 5, not a courtesy.** With these three conditions,
the two settings combinations where enrollment has been completed have no enable link — correctly,
there is nothing to enrol in. Their route back to `@@setup-two-factor-authentication` (for a new
device, or to regenerate codes) is the regenerate action, which points at that same form (RECOV-06).
If D-15 is skipped and the regenerate action keeps the disable link's condition, two of the four
matrix cells lose every route to the enrollment form. The matrix test is what pins this.
</planner_notes>
