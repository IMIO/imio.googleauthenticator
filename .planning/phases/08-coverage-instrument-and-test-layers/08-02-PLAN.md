<objective>
Move the GenericSetup profile install from a Browser-driven `portal_quickinstaller` round trip
inside the test layer to the layer's own `setUpPloneSite` hook, delete the helper and all 21 of its
call sites, and rewrite the installedness assertion to test what this package actually controls.

Purpose: `tests/base.py`'s install helper drives a testbrowser through
`prefs_install_products_form` once per test class, and that browser request commits — which is the
state leak QUAL-05 exists to close. Its own in-file comment admits the layer does not apply the
profile correctly; `setUpPloneSite` is the framework hook that was always the right answer.
QUAL-07 lands in the same plan because it is not optional here: the moment the helper disappears,
nothing updates `portal_quickinstaller`, so `test_product_is_installed` fails on an otherwise
correct change (RESEARCH.md Pattern 2 verified `applyProfile` never calls `installProduct`).
Output: the install runs once per layer through the supported hook; installedness is asserted
through plugin registration, registry records and the browser layer.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test layer -> code under test | A test layer that leaks committed state across tests can make a broken authorization guard appear enforced. The boundary is the isolation guarantee itself. |
| test assertion -> install correctness | `test_product_is_installed` is the only assertion standing between a broken GenericSetup profile and a shipped release with no PAS plugin registered. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-04 | Elevation of privilege | test-layer isolation (`tests/base.py` install helper committing inside the layer) | high | mitigate | Delete the Browser-driven install and move to `setUpPloneSite`, removing the per-test-class commit that leaks state forward. The security-relevant failure mode is test-time false confidence: a guard that passes only because a previous test's committed state happened to satisfy it. Plan 08-03 completes the fix by moving every test onto the per-test `DemoStorage` layer. |
| T-08-05 | Tampering | the rewritten `test_product_is_installed` assertions | high | mitigate | Each of the three assertions gets an explicit non-vacuity control (Task 2 step 6) — broken one at a time, confirmed red, restored. A vacuous replacement is worse than the quickinstaller assertion it replaces, because it reads as coverage of the install path while proving nothing. |
| T-08-06 | Tampering | a production defect revealed by the install-mechanism change | high | mitigate | D-08 governs: fixed in-phase, code-side if the fault is code-side. Explicitly prohibited (see `must_haves.prohibitions`): adjusting a test's expectation instead of the code, and re-introducing a swallowed exception or loosening a fail-closed path to make a test pass. `_dont_swallow_my_exceptions = True` stays True. |
| T-08-07 | Information disclosure | `setUpPloneSite` -> `setuphandlers.setupVarious`, which generates the site-wide URL-signing secret | low | accept | The generated `ska_secret_key` lives in the test layer's throwaway `DemoStorage` and is never printed. This plan changes *when* the profile runs, not what it stores or logs, and the seed encryption key still comes from the `[testenv]` environment variable rather than the ZODB. |
</threat_model>
